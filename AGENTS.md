# AGENTS.md

pnpm + Turborepo monorepo for a storage-drive inventory app. Workspaces (dirs != package names):

- `drives-server` → `@drives/drives-server` — NestJS 12 API, Sequelize/Postgres
- `drives-ui` → `@drives/drives-ui` — Next.js 16 + Refine + Ant Design
- `drives-policy` → `@drives/policy` — Cerbos authorization policies (YAML, no build)

Node 24 / pnpm 12.14.0 are pinned (`packageManager`, `.node-version`). Use `pnpm`, never `npm`; the root `README.md` is stale (`server` dir / npm instructions).

## Commands (run from root)

```bash
pnpm install
pnpm turbo run <task>                      # dev | build | lint | format | test
pnpm --filter @drives/drives-server test   # one workspace
pnpm --filter @drives/drives-server exec vitest run src/modules/physical-drive/physical-drive.service.spec.ts   # one test file
pnpm --filter @drives/drives-server start:dev   # nest start --watch
pnpm --filter @drives/drives-ui start:dev       # refine dev (not `next dev`)
```

CI (`.github/workflows/ci.yml`) runs `lint` → `build` → `test` for the whole workspace. The UI uses a flat `eslint.config.mjs` with `eslint-config-next`; do not use the removed `next lint` command.

Tests use **Vitest everywhere** (not Jest). `drives-server/test/jest-e2e.json` is stale. Server Vitest needs `unplugin-swc` (decorators) — keep the plugin when editing `vitest.config.mts`. Server specs import from `vitest` explicitly; UI uses jsdom + `src/test/setup.ts`.

## Backend (`drives-server`)

- Global route prefix `api` + URI versioning default `v1` → `/api/v1/...`. Exceptions: `/system/version`, `/system/status`, `/health*` (`VERSION_NEUTRAL`). Swagger only in `development` at `/api/docs`.
- IDs are **UUIDv7** (DB default `uuidv7()`); use `ParseUUIDPipe({ version: '7' })` and `@IsUUID('7')`.
- Modules live in `src/modules/<resource>` with `controller` / `service` / `dto` / `entities`. Register new modules in `src/app.module.ts`.
- Controllers are guarded by `@UseGuards(KeycloakAuthGuard, CerbosGuard)`, both `@Public()` and `@CheckPolicy(...)` decorators control access. Global `APP_GUARD` is `KeycloakAuthGuard`. Both guards short-circuit when `DRIVES_BACKEND_AUTH_ENABLED=false` (set in local `.env`; `app.config.ts` parses it to a real boolean, so the string `"false"` is not mistaken for truthy), which is why almost every route carries `@Public()`.
- Server tests run with `NODE_ENV=test`, so `database.config.ts` switches to in-memory sqlite — unit tests need no Postgres. Specs mock models with `getModelToken`.
- Responses: annotate controllers with `@Serialize(SomeResponseDto)`; DTOs must use `@Expose()` (extraneous fields are stripped). List endpoints return `PaginatedResponse` `{ data, meta: { totalItems, itemCount, itemsPerPage, totalPages, currentPage } }`.
- Entities extend `shared/entities/base.model.ts` (UUIDv7 `id` + auto-increment `displayKey`), use `underscored: true`.
- Query params: `pageNumber`, `pageSize`, `sortField`, `sortOrder` and the structured **`filters`** param (a JSON object/array or repeated params) — see `src/modules/pagination/dto/pagination-query.dto.ts`. Filtering is a first-class **`PaginationModule`** (`@Global`): conditions are normalized to `FilterCondition[]` and **ANDed** (`src/modules/pagination/builders/filter-normalizer.ts` + `where-clause.builder.ts`); `id` becomes `id IN (...)`, and `between` requires two comma-separated values. Operators are `eq|ne|gt|gte|lt|lte|in|like|between` (case-insensitive; unknown operators are a 400, `like` is a case-sensitive `%value%` match). Multi-sort supports comma-separated `sortOrder` values paired with `sortField`. The pagination service merges query filters with service-specific `where` clauses via `Op.and`, maps unknown-column/invalid-text DB errors to 400, and defaults the order to `displayKey ASC`. `pageSize` has no max. `@Public()` GET-list/create/update/delete is common.
- Binary memory-unit conversion lives in `src/lib/utils/human.readable.bytes.converter.ts` (`toBytes`/`fromBytes`/`isBinaryUnit`); RAM is stored as a value + binary unit and mirrored into a denormalised `absolute_*memory` BIGINT via a `@BeforeSave` hook (the getter coerces back to `number` because `pg` returns BIGINT as a string).

### Physical servers & server slots

- `PhysicalServer` (`physical_servers`): `hostname` (unique), `memoryValue` + `memoryUnit` (`MiB|GiB|TiB`, default `GiB`), denormalised `absoluteMemory` (BIGINT, `@BeforeSave`/`toBytes`), `rackUnitPosition` (unique per rack), FKs `operatingSystemId`, `rackId`. `@HasMany ServerSlot` and `@HasMany PhysicalCpu`. The former `cpuModelId`/`cpuCount` columns were dropped (see below).
- `ServerSlot` now lives inside this module (`entities/server-slot.entity.ts`, table `server_slots`): `slotLabel`, optional `pcieBusAddress`, FK `serverId`, FK `supportedInterfaceId`; composite unique `(server_id, slot_label)` (`server_slots_label_unique_idx`). It has **no REST resource of its own** — slots are created/updated only through the owning `physical-servers` payload via `ServerSlotService.syncForServer`. The standalone `server-slot` module/controller/DTOs were deleted.
- `PhysicalServer` list/create/update eager-load `cpus` (each with `cpuModelId`) and `slots` (with `supportedInterfaceId`/`pcieBusAddress`) so consumers get both owned-child trees in one request.
- **CPU ownership**: a server owns its installed CPU chips via `physical_cpus.physical_server_id` (nullable UUID, FK → `physical_servers` ON DELETE SET NULL; index `physical_cpus_physical_server_id_idx`). The `create-physical-cpus` migration (`20260710030320`) runs **after** `create-physical-servers` (`20260710024640`) so it defines the FK in its own table. create/update accept an optional `cpuIds: string[]` which **replaces the full set** of chips assigned to the server; `PhysicalServerService.syncCpus` validates them (duplicates rejected → `BadRequestException`; unknown → `NotFoundException`; already owned by another server → `ConflictException`), releases unlisted chips and assigns the listed ones in the server's transaction. `cpuIds` is optional (a server may have no inventoried chips yet).
- `CpuModel` (`cpu_models`) holds `physicalCores` and `threads` (per chip/socket) and is referenced by `PhysicalCpu.cpuModelId`; a host's total hardware threads is the sum of its installed chips' `cpuModel.threads`.

### Physical CPUs

- `PhysicalCpu` (`src/modules/physical-cpu`, table `physical_cpus`, migration `20260710030320-create-physical-cpus.js`) is the per-instance counterpart to `CpuModel`, mirroring the `drive-models` → `physical-drives` pattern. Fields: `label` (STRING(40), unique, auto-generated), `serialNumber` (STRING(64), unique), `acquisitionCost` DECIMAL(12,2), `purchaseDate`/`warrantyExpiryDate` (DATEONLY), FKs `cpuModelId` (→ `CpuModel`, RESTRICT), `retailerVendorId` (→ `Vendor`, RESTRICT), `currencyId` (→ `Currency`, RESTRICT); virtual `title` = `serialNumber`. Indexes `physical_cpus_serial_number_idx` (unique), `physical_cpus_cpu_model_idx`, `physical_cpus_financial_idx`.
- `@BeforeValidate generateAssetLabel` builds the label as `MFG-MODEL-YYYYMMDD-SEQ` (no capacity segment), resolving the manufacturer from `CpuModel.vendor`. Seeder `20261017012320-seed-test-physical-cpus.js` supplies labels explicitly (bulkInsert bypasses hooks). Policy `drives-policy/policies/physical-cpus.yaml`; UI CRUD at `/physical-cpus/*` (menu under **Hardware**).
- Installed chips are linked back to their owning server via `PhysicalCpu.physicalServerId` (nullable FK → `physical_servers`, ON DELETE SET NULL; DB constraint in this resource's own migration). To avoid an entity import cycle with `PhysicalServer`'s `@HasMany`, this side declares the column without `@ForeignKey`/`@BelongsTo`; `PhysicalServer` owns the `@HasMany(() => PhysicalCpu, { foreignKey: 'physicalServerId' })` side. Assignments are driven by the `physical-servers` payload, not this resource.

### Virtual servers (guests)

- Module `src/modules/virtual-server` — `VirtualServerController`/`VirtualServerService`/`dto`/`entities` plus the nested `PassthroughSlotService`. Registered in `app.module.ts`; `PhysicalCpu` and `CpuModel` are in its `SequelizeModule.forFeature` list (needed for the vCPU-capacity include).
- `VirtualServer` (`virtual_servers`): `vmid` (nullable; partial unique `(host_server_id, vmid)` where `vmid IS NOT NULL` → `virtual_servers_vmid_unique_idx`), `hostname` (globally unique), `type` ENUM `VM|CONTAINER` (default `VM`), `allocatedVcpus`, `allocatedMemoryValue` DECIMAL(10,2) + `allocatedMemoryUnit` ENUM `MiB|GiB|TiB` (default `GiB`), denormalised `absoluteAllocatedMemory` (BIGINT, `@BeforeSave`/`toBytes`), `isActive` BOOLEAN default `true`, `notes`, FKs `hostServerId` (→ `PhysicalServer`, RESTRICT) and `operatingSystemId` (→ `OperatingSystem`, RESTRICT). Indexes `virtual_servers_host_server_idx`, `virtual_servers_operating_system_id_idx`.
- Reads (`findAll`/`findOne`) eager-load `PhysicalServer`, `OperatingSystem`, and the guest's passthrough slots (each with its `ServerSlot`) via `readIncludes`.
- create/update run inside a transaction and enforce two host-capacity rules (both throw `ConflictException`):
  - **Memory — aggregate, active guests only** (`assertWithinHostCapacity`): locks the host `PhysicalServer` row (`LOCK.UPDATE`) so concurrent writes on one host serialize, sums `absoluteAllocatedMemory` over the host's **active** guests (`isActive: true`, excluding the row being updated), and adds the requested bytes only when the guest being saved is active (create defaults to active; update uses `updateDto.isActive ?? existing.isActive`). The total must be ≤ host `absoluteMemory`. Inactive guests are powered off and reserve no RAM.
  - **vCPU — per-VM, NOT aggregate** (`assertWithinHostThreadCapacity`): a single guest's `allocatedVcpus` must be ≤ the host's total hardware threads, i.e. the sum of the host's installed `PhysicalCpu`s' `cpuModel.threads`. Loads the host with `include: [{ model: PhysicalCpu, include: [CpuModel] }]`; the check is skipped when `totalThreads` is `0` (incomplete CPU data) so it never blocks on missing specs. Over-subscription **between** guests is intentionally allowed (e.g. two 64-vCPU guests on a 64-thread host).

### Passthrough slots

- Maps a host backplane slot (`server_slots`) through to a guest as hardware passthrough. Table `passthrough_slots` (migration `20260710041000-create-passthrough-slots.js`); entity `PassthroughSlot` (`entities/passthrough-slot.entity.ts`), service `PassthroughSlotService` (`passthrough-slot.service.ts`), request DTO `PassthroughSlotDto` (`dto/passthrough-slot.dto.ts`), response `PassthroughSlotResponseDto`. Naming deliberately dropped the earlier `VirtualServer`-prefixed classes and `virtual_server_passthrough_slots` table to match the `server-slot.*` convention.
- Columns `virtual_server_id` (FK → `virtual_servers`, ON DELETE CASCADE) and `server_slot_id` (FK → `server_slots`, ON DELETE CASCADE); index `passthrough_slots_virtual_server_id_idx` plus **unique** `passthrough_slots_server_slot_id_unique_idx` which enforces "one host slot → at most one guest" globally.
- **Not a standalone REST resource** — carried as the nested `passthroughSlots` array on virtual-server create/update. `PassthroughSlotService.syncForVirtualServer(virtualServerId, hostServerId, slots, transaction?)` reconciles the full desired set: rejects duplicate slot refs in the payload, verifies every slot belongs to the host, rejects slots already mapped to another guest, then deletes removed and inserts new mappings.
- **Guests of `type: CONTAINER` may not have passthrough slots.** `create`/`update` throw `BadRequestException` when a container is given a non-empty payload; converting a VM → CONTAINER clears the guest's existing mappings even when `passthroughSlots` is omitted. On host change, stale mappings are likewise cleared (an omitted payload during a host change is treated as "clear all").
- No Cerbos policy of its own (it is governed by the `virtual-servers` resource).

### Storage pools & pool types

- `PoolType` (`src/modules/pool-type`, table `pool_types`, migration `20260710042640-create-pool-types.js`) is a standard lookup resource (`name` STRING(32) unique, `managed` BOOLEAN default false, VIRTUAL `title`) mirroring `storage-types`/`bus-protocols`; seeded by `20260710023000-seed-pool-types.js` with `ZFS|BTRFS|CEPH_OSD_POOL|MDRAID|RAW_JBOD` (`managed: true`). Cerbos policy `drives-policy/policies/pool-types.yaml` (managed rows cannot be edited/deleted). Registered in `app.module.ts` + `database.module.ts`.
- `StoragePool` (`src/modules/storage-pool`, table `storage_pools`): `poolName` STRING(64), `encryptionEnabled` (default false), `poolTypeId` (FK → `PoolType`, RESTRICT) — the former `pool_type` ENUM was replaced by this lookup FK (migration `20260710044320-create-storage-pools.js` creates only `pool_type_id` + index `storage_pools_pool_type_id_idx`). A pool no longer carries `server_id`/`virtual_server_id`: `poolTypeId` is exposed as a plain FK id (no eager-loaded `PoolType`, per the lookup convention) and validated on write.
- **Hosting is an append-only event log**, not a column. `StoragePoolHost` (`src/modules/storage-pool/entities/storage-pool-host.entity.ts`, table `storage_pool_hosts`, migration `20260710050000-create-storage-pool-hosts.js`) records `eventType` ENUM `IMPORT|EXPORT`, `eventTimestamp` (DATE, default now), `notes`, `storagePoolId` (FK → `StoragePool`, CASCADE) and the polymorphic host `physicalServerId` XOR `virtualServerId` (FKs RESTRICT, enforced by the `storage_pool_hosts_host_exclusivity_check` DB constraint). There is **no `is_active` flag / partial unique index**: a pool's **current host is derived** from its latest event (`IMPORT` ⇒ attached to that host, `EXPORT`/no events ⇒ detached), ordered by `eventTimestamp DESC, displayKey DESC`. The "at most one host" invariant is enforced in `StoragePoolService` inside a transaction that locks the pool row (`LOCK.UPDATE`) — mirroring the virtual-server capacity guard.
- Endpoints: `POST /storage-pools/:id/import` (`ImportStoragePoolDto`, exactly one host, 409 if already attached) and `POST /storage-pools/:id/export` (`ExportStoragePoolDto`, host taken from the current event, 409 if detached) append events; `GET /storage-pools/attached?physicalServerId=|virtualServerId=` returns pools whose latest event attaches them to that host (**declared before `GET :id`** so it is not swallowed by the UUID param route). Reads expose a derived `currentHost: { type: 'PHYSICAL'|'VIRTUAL', serverId, hostname } | null`; single-record reads also include the ascending `hosts` timeline. `create` accepts an optional `serverId`/`virtualServerId` to record an initial IMPORT (detached otherwise); `update` cannot change the host (use import/export). Cerbos policy `drives-policy/policies/storage-pools.yaml` lists `import`/`export`.
- Test fixtures `20261017024640-seed-test-storage-pools.js` (8 pools) + `20261017030320-seed-test-storage-pool-hosts.js` (IMPORT/EXPORT events, incl. a `ash-storage-01 → ash-compute-01` move, Frankfurt physical/guest attachments, and one detached pool) resolve `pool_type_id`/host ids by business key; no test seeder is needed for `pool_types` itself.

### Physical drive locations

- `PhysicalDriveLocation` (`src/modules/physical-drive/entities/physical-drive-location.entity.ts`, table `physical_drive_locations`, migration `20260710064000-create-physical-drive-locations.js`) is an **append-only location log** tracking which datacenter a drive sits in over time, mirroring `storage_pool_hosts`. Fields: `locatedAt` (DATE, default now), `notes`, FKs `physicalDriveId` (→ `PhysicalDrive`, CASCADE) and `datacenterId` (→ `Datacenter`, RESTRICT). Indexes `physical_drive_locations_history_idx` (`physical_drive_id, located_at`) + `physical_drive_locations_datacenter_id_idx`. No enum, no `is_active` flag, no partial unique index.
- **Current location is derived** from the latest row (`locatedAt DESC, displayKey DESC`); the "one current location" invariant is enforced in `PhysicalDriveService.recordLocation` inside a transaction that locks the drive row (`LOCK.UPDATE`). Recording the drive's current datacenter is rejected with a 409 so the log stays meaningful, and a move appends a new row. A drive with **no rows is unassigned** (there is no explicit detach event). Both `recordLocation` and `relocateDrive` reject a drive that is currently mounted in a server slot (`ConflictException`) — it must be unmounted from the server's Assign Drives page first.
- **Not a standalone REST resource** — nested under `physical-drives`. `POST /physical-drives/:id/locations` (`CreatePhysicalDriveLocationDto`: required `datacenterId`, optional `notes`/`locatedAt`) appends an event. `POST /physical-drives/:id/relocations` (`RelocateDriveDto`, authenticated, `@CheckPolicy('locate','physical-drives')`) is the Relocate Drive workflow endpoint: same location append but rejects mounted drives and supports drives with **no current location** (assigns their first location). Reads expose a derived `currentLocation: { id, datacenterId, code, name, locatedAt, notes } | null`, and single-record reads include the ascending `locations` timeline. The paginated list accepts a derived **`filters`** condition `{"field":"currentLocation","operator":"in","value":"<comma-separated datacenter ids>"}`: `PhysicalDriveService.findAll` resolves the drives whose latest event is one of those datacenters and rewrites it into an `id IN (…)` clause before delegating to the pagination service (an empty match becomes `id IN (NULL)` → 0 rows). It also accepts **`unassigned=true`** (drives with no location rows, via a `NOT IN` subquery) and stamps derived `currentLocation`, `currentLifecycle` and `currentAssignment` on every listed drive. `PhysicalDrive` owns `@HasMany(() => PhysicalDriveLocation, { as: 'locations' })`; the module registers `PhysicalDriveLocation` + `Datacenter`.
- **Dashboard distribution**: the former `GET /physical-drives/stats` endpoint was removed. `DashboardService` now derives the `driveDistribution` section of `GET /dashboard/summary` from the same batched `PhysicalDriveService.getCurrentLocationMap` helper used by `findAll`, keeping dashboard aggregation out of `PhysicalDriveService`. The donut/legend card (`src/app/dashboard/_components/physical-drive-distribution.tsx`, presentational + Recharts) deep-links datacenter legend rows into `/physical-drives` with the `currentLocation`/`in` filter.
- Cerbos: the resource has no policy of its own — it reuses `drives-policy/policies/physical-drives.yaml` (which now includes a `locate` action on the admin rule). Test fixture `20261017032000-seed-test-physical-drive-locations.js` assigns a datacenter to 46 of the 50 seeded drives (rotating across `VA-ASH-1`/`GB-SLO-1`/`DE-FRA-1`), exercises a `VA-ASH-1 → GB-SLO-1` move, and deliberately leaves 4 drives (`TESTDRV-0047..0050`) unassigned.
- UI: the list shows the derived `currentLocation` column (an `Unassigned` tag when null, else `@components/linked-label` → `/datacenters/show/:id`) with a datacenter `FilterDropdown` bound to the `currentLocation`/`in` filter, plus a **Clear Filters** header button (`setFilters([], "replace")`); the show page has a "Location History" card (`src/app/physical-drives/_components/physical-drive-location-actions.tsx` + `…-locations-timeline.tsx`) rendered **newest-first** with a `Current` tag on the derived current event, plus a **Lifecycle History** card (`…-lifecycle-timeline.tsx`) fed by `GET /physical-drives/:id/lifecycle` and also rendered newest-first; the datacenter show page instead deep-links into that paged, filtered list via `stringifyTableParams({ sorters: [], filters: [{ field: 'currentLocation', operator: 'in', value: [id] }] })` (no bulk row load — the old `@components/located-physical-drives` table was removed). **No new Refine resource** — locations ride on `physical-drives`.

### Physical drive → server-slot assignments

- `ServerSlotAllocation` (`src/modules/server-slot-allocation/`, table `server_slot_allocations`, migration `20260710033640-create-server-slot-allocations.js`) is an **append-only MOUNT/UNMOUNT event log** seating a `PhysicalDrive` in a `ServerSlot`. Fields: `actionType` ENUM `MOUNT|UNMOUNT`, `timestamp` (DATE, default now), FKs `serverSlotId` (→ `ServerSlot`, CASCADE), `physicalDriveId` (→ `PhysicalDrive`, CASCADE), `userId` (→ `User`, **RESTRICT** — the accountability anchor). Indexes `(server_slot_id, timestamp)`, `(physical_drive_id, timestamp)`, `(user_id)`. No `is_active` flag / partial unique.
- **Current state is derived** from the latest event per key (`timestamp DESC, displayKey DESC`): a drive's latest `MOUNT` ⇒ seated in that slot, latest `UNMOUNT`/no row ⇒ unassigned; a slot's latest `MOUNT` ⇒ holds that drive, else empty. `ServerSlotAllocationService` (`getSlotOccupancyMap`, `getLatestEventPerKey`, `getLatestLocationPerDrive`) derives these in one query-per-key and is the single authority for the mapping.
- **Writes go through mount/unmount/save only** — the ledger REST resource is **read-only** (`GET /server-slot-allocations` list + `GET /:id`; the old `POST`/`PUT`/`DELETE` and the create/update DTOs were removed). `POST /physical-servers/:id/slots/:slotId/mount` (`MountDriveDto.physicalDriveId`) and `POST /physical-servers/:id/slots/:slotId/unmount` both return the refreshed **slot assignment board**; both are authenticated (not `@Public()` — the actor is taken from the token as `user.dbUser.id ?? user.id`) and gated by `@CheckPolicy('mount'|'unmount', 'server-slot-allocations')` (policy `drives-policy/policies/server-slot-allocations.yaml`). `PUT /physical-servers/:id/slot-assignments` (`SaveSlotAssignmentsDto.assignments: [{ slotId, physicalDriveId }]`, gated by `@CheckPolicy('save', …)`) is the **bulk staged save**: the body is the *complete* desired seating for the server, so omitted slots are emptied. It locks the server row then all server slots then the involved drives, validates slot ownership / no duplicate slot-or-drive / drive location-in-datacenter, and reconciles the derived current state against the desired state as `UNMOUNT`s (first) then `MOUNT`s (so a MOUNT is always the latest event) — a drive mounted on another server is moved. These generic paths are lifecycle-aware: unmounting an `IN_SERVICE` drive appends `DEPROVISION`; seating a non-`IN_SERVICE` drive appends `PROVISION`; a move appends `DEPROVISION` + `PROVISION` (context in `contextMetadata`, `triggeredBy: 'slot-assignment'`).
- **Invariants** (enforced in a transaction that row-locks the slot then the drive, mirroring the location/pool guards): slot must belong to the addressed server (`BadRequestException`); the drive must have a recorded current location **in the same datacenter** as the server (server → rack → datacenter; `ConflictException`, drives with no location are ineligible); mounting into an occupied slot is a `ConflictException`; and a drive occupies at most one slot — if it is currently mounted elsewhere the move appends `UNMOUNT(old)+MOUNT(new)` in one transaction.
- **Drive Allocation workflow endpoint**: `POST /physical-servers/allocations` (`AllocateDrivesDto`: required `datacenterId`; optional `sourceServerId` + `detachDriveIds`; optional `targetServerId` + `assignments: [{ slotId, physicalDriveId }]`; `unseatedDriveStates: [{ physicalDriveId, eventType, explanation? }]` for detached drives that stay unseated), authenticated and gated by `@CheckPolicy('save','server-slot-allocations')`. `ServerSlotAllocationService.allocateDrives` runs one transaction that locks servers → target slots → involved drives (deterministic id order), verifies both servers and every seated drive belong to the datacenter, detaches only drives currently seated in the source, allows only unseated or source-detached drives to be seated, rejects occupied target slots, and appends `UNMOUNT`s before `MOUNT`s. It also keeps the lifecycle ledger consistent: **detached → mounted** records `DEPROVISION` then `PROVISION`; **unseated → mounted** records `PROVISION` unless the drive is already `IN_SERVICE`; **detached → unseated** requires exactly one state from the curated set (`DEPROVISION|DEGRADE|FAIL|RETIRE|SCRAP_SHRED|LOST`, `RMA_INITIATE` deliberately excluded) and stores the optional explanation in `contextMetadata.reason` alongside the source/target context. Missing/extra states, curated-set violations and illegal transitions fail the whole transaction (400/409). Existing target occupants (slots omitted from `assignments`) are left untouched; detached drives not assigned are left unseated. Returns `{ source, target, unmountedDriveIds, mountedDriveIds }` with refreshed boards.
- **Board read**: `GET /physical-servers/:id/slot-assignment-board` (`SlotAssignmentController`, `@Serialize(SlotAssignmentBoardResponseDto)`) returns `{ server: { id, hostname, rackId, rackName, datacenterId, datacenterCode, datacenterName }, slots: [{ id, slotLabel, pcieBusAddress, supportedInterfaceId, occupancy: { allocationId, physicalDriveId, driveLabel, serialNumber, driveModelId, driveModelName, assignedAt } | null }], freeDrives: [{ id, label, serialNumber, driveModelId, driveModelName }], summary: { totalSlots, occupiedSlots, emptySlots, freeDrives } }`. `freeDrives` = drives whose latest location is the server's datacenter **and** which are not currently mounted.
- **Reverse projection**: `ServerSlotAllocationService.getCurrentAssignmentsForDrives(driveIds)` returns a `Map<driveId, { allocationId, slotId, slotLabel, serverId, serverHostname, assignedAt }>` (drives whose latest event is an UNMOUNT / have no events are absent). `PhysicalDriveModule` imports `ServerSlotAllocationModule`; `PhysicalDriveService` uses it to stamp a derived **`currentAssignment`** onto drive reads (`findAll`, `findOne` + the `POST /:id/locations` / `:/id/relocations` responses) — the drive show page renders a **Current Server** field linking to `/physical-servers/show/:id` with the slot label.
- `ServerSlotAllocationModule` registers `ServerSlotAllocation, ServerSlot, PhysicalServer, PhysicalDrive, PhysicalDriveLocation, DriveModel, Rack, Datacenter, User` and exports the service.
- Guard note: with `DRIVES_BACKEND_AUTH_ENABLED=false` the `KeycloakAuthGuard` now JIT-upserts its mock user (`00000000-…`) too, so `user_id` FK writes resolve locally.
- UI: `src/app/physical-servers/assign/[id]/page.tsx` renders `_components/slot-assignment/` — a **staged** drag-and-drop board (`@dnd-kit/core`) reached from the physical-server show page's **Assign Drives** button (its own `<Breadcrumb>` matching the rest of the app). Free drives (same datacenter) are draggable chips; slots are drop zones grouped by `supportedInterfaceId` (`occupied` slots disable the drop target). Drags mutate a local `draft` (slot→drive map) only — the bottom action bar's **Save changes** calls `PUT /slot-assignments` via `useCustomMutation` with the whole seating (Discard reverts; Refresh re-fetches and resets). All colors come from antd `theme.useToken()` so dark mode is readable. The board is derived from `query.data?.data` (Refine's `useCustom` returns a truthy `EMPTY_OBJECT` `result.data` while loading). Test fixture `20261017033640-seed-test-server-slot-allocations.js` (also seeds the mock user row) selects provisioned drives by their current datacenter and supplies six live mounts (two per datacenter) plus one VA drive that is mounted then unmounted, so every selected drive's lifecycle state stays consistent (six `IN_SERVICE`, one `IN_INVENTORY`).

### Drive lifecycle events

- `DriveLifecycleEvent` (`src/modules/drive-lifecycle-event`, table `drive_lifecycle_events`, migration `20260710005000-create-drive-lifecycle-events.js`) is an **append-only lifecycle log** (acquisition → provisioning → degradation → failure → RMA → retirement → scrap). Fields: `eventType` ENUM (`ACQUIRE|PROVISION|DEPROVISION|DEGRADE|RECOVER|FAIL|RMA_INITIATE|RMA_SHIP|RMA_APPROVE|RMA_REJECT|RMA_REPLACE|RMA_CLOSE|RETIRE|SCRAP_SHRED|LOST|INSPECT|NOTE`), `eventTimestamp` (DATE, default now), `triggeredBy` STRING(128) (agent/operator label), `contextMetadata` JSONB, FKs `physicalDriveId` (→ `PhysicalDrive`, RESTRICT), `performedByUserId` (→ `User`, SET NULL) and nullable `replacementPhysicalDriveId` (→ `PhysicalDrive`, SET NULL; the successor shipped on `RMA_REPLACE`). Indexes `drive_lifecycle_history_idx` (`physical_drive_id, event_timestamp, display_key`), `drive_lifecycle_performed_by_idx`, `drive_lifecycle_replacement_drive_idx`. `INSPECT`/`NOTE` are **informational** (never change state, always allowed, even on terminal drives). Warranty-claim integration (`warranty_claims.triggering_event_id` FK, `src/modules/warranty-claim`) exists but is deliberately disconnected for now: the two RMA logs are **independent** (drives carry their own `RMA_*` lifecycle events; claims carry their own tracking events), and `replacementPhysicalDriveId` is recorded on **both** the `RMA_REPLACE` lifecycle event (drive lineage) and the `REPLACEMENT_RECEIVED` claim event (vendor fulfillment).
- **State is derived, never stored**: `DriveLifecycleState` = `UNRECEIVED|RECEIVED|IN_INVENTORY|IN_SERVICE|DEGRADED|FAILED|IN_RMA|RETIRED|SCRAPPED|REPLACED|LOST` is computed from the latest state-changing event (`eventTimestamp DESC, displayKey DESC`; no events ⇒ `UNRECEIVED`, informational events ignored). `drive-lifecycle-state-machine.ts` owns the mapping (`stateForEvent`, `deriveStateFromEvents`, `allowedEventsFor`, `canTransition`, `isTerminalState`); terminal states are `SCRAPPED|REPLACED|LOST`. Both ledgers share the table-driven, dependency-free `src/lib/state-machine/create-event-state-machine.ts` factory (compile-time exhaustive `stateByEvent`/`transitions` records); their specs assert the full state × event matrix.
- **Writes are append-only** (`recordEvent`, no `update`/`delete`): a transaction row-locks the drive (`LOCK.UPDATE`), derives the current state, rejects an illegal transition or a timestamp earlier than the latest event (`ConflictException`), enforces the `RMA_REPLACE` replacement rules (required for `RMA_REPLACE`, rejected otherwise, not self, must exist, not already linked to another RMA) and `performedByUserId` existence, then inserts and returns the refreshed timeline.
- Endpoints: `GET /drive-lifecycle-events` (paginated; dedicated filters `physicalDriveId`/`eventType`/`triggeredBy`/`performedByUserId`/`replacementPhysicalDriveId` + `eventTimestampFrom`/`To`) and `GET /drive-lifecycle-events/:id`, both `@Public()`. Nested `DriveLifecycleController` (`@Controller('physical-drives')`): `GET /physical-drives/:id/lifecycle` (`@Public()`, `DriveLifecycleTimelineResponseDto`) and `POST /physical-drives/:id/lifecycle-events` (`CreateDriveLifecycleEventDto`, **authenticated**, `@CheckPolicy('create','drive-lifecycle-events')`) which returns the refreshed timeline. The actor comes from the token (`user.dbUser.id ?? user.id`; `triggeredBy` falls back to the body/username).
- Reads expose a derived **`currentLifecycle`** on every `PhysicalDriveResponseDto` (list + show), including the state-changing **`allowedEvents`** for that state: `PhysicalDriveService` injects `DriveLifecycleEventService.getCurrentLifecycleMap(driveIds)` and stamps it, mirroring `currentAssignment`/`currentLocation`. `PhysicalDriveModule` imports `DriveLifecycleEventModule`. Policy `drives-policy/policies/drive-lifecycle-events.yaml` (admin `create`/`show`/`list`, owner/viewer read-only). Test fixture `20261017035320-seed-test-drive-lifecycle-events.js` appends 113 static events across the 50 drives (every drive `ACQUIRE`d, 40 provisioned, plus the degrade/fail/RMA-replacement/retire/scrap/lost histories and an additional IN_RMA drive; resolves drives by id order and upserts the mock user). It then appends alignment `DEPROVISION` events for provisioned drives that are **not** currently seated (derived from `server_slot_allocations`, currently 23 → 136 total), keeping `IN_SERVICE` consistent with seating.
- **Acquisition workflow endpoint**: `POST /physical-drives/acquisitions` (`CreateDriveAcquisitionDto` = `CreatePhysicalDriveDto` + required `datacenterId` and optional `locationNotes`/`locatedAt`) is the one multi-record write. `PhysicalDriveService.acquireDrive` runs one transaction: serial-uniqueness check, FK/datacenter validation, create the drive, insert the initial `physical_drive_locations` row, then append the `ACQUIRE` event via `DriveLifecycleEventService.recordEventInTransaction`. It is **authenticated** and gated by `@CheckPolicy('create','physical-drives')`; the actor comes from the token. `recordEvent` now delegates to `recordEventInTransaction` so workflows can join a caller-owned transaction.

### Warranty claims

- `WarrantyClaim` (`src/modules/warranty-claim`, table `warranty_claims`, migration `20260710010640-create-warranty-claims.js`) is the **claim header**: immutable identity/details captured when the RMA is opened — `physicalDriveId` (→ `PhysicalDrive`, RESTRICT; the failed drive), optional `triggeringEventId` (→ `DriveLifecycleEvent`, RESTRICT), `handledByVendorId` (→ `Vendor`, RESTRICT), `rmaTrackingNumber` STRING(64), `notes` TEXT. There is **no stored `claim_status`/`submitted_at`/`resolved_at`** (the old columns were dropped): status and lifecycle timestamps are derived from the tracking log. Indexes `warranty_claims_trigger_event_idx`, `warranty_claims_physical_drive_idx`.
- `WarrantyClaimEvent` (`entities/warranty-claim-event.entity.ts`, table `warranty_claim_events`, migration `20260710012320-create-warranty-claim-events.js`) is an **append-only tracking log** of what happened to a claim: `eventType` ENUM (`SHIPPED_TO_VENDOR|APPROVED|REJECTED|REPLACEMENT_RECEIVED|CLOSED|NOTE`), `eventTimestamp` (DATE, default now), `notes` TEXT, `performedByUserId` (→ `User`, SET NULL) and nullable `replacementPhysicalDriveId` (→ `PhysicalDrive`, SET NULL; the successor received on `REPLACEMENT_RECEIVED`). FKs `warrantyClaimId` (→ `WarrantyClaim`, CASCADE). Indexes `warranty_claim_events_history_idx` (`warranty_claim_id, event_timestamp, display_key`), `warranty_claim_events_performed_by_idx`, `warranty_claim_events_replacement_drive_idx`. `NOTE` is **informational** (never changes status).
- **Status is derived, never stored**: `WarrantyClaimStatus` = `SUBMITTED|SHIPPED_TO_VENDOR|APPROVED|REJECTED|REPLACEMENT_RECEIVED|CLOSED` is computed from the latest state-changing event (`eventTimestamp DESC, displayKey DESC`; no events ⇒ `SUBMITTED`, informational events ignored). `warranty-claim-state-machine.ts` owns the mapping (`statusForEvent`, `deriveStatusFromEvents`, `allowedEventsFor`, `canTransition`, `isTerminalStatus`); `CLOSED` is terminal. It reuses the shared `src/lib/state-machine/create-event-state-machine.ts` factory and its spec covers the full status × event matrix.
- **Writes are append-only** (`WarrantyClaimEventService.recordEvent`, no update/delete): a transaction row-locks the claim (`LOCK.UPDATE`), derives the current status, rejects an illegal transition or a timestamp earlier than the latest event (`ConflictException`), enforces the `REPLACEMENT_RECEIVED` replacement rules (required for `REPLACEMENT_RECEIVED`, rejected otherwise, not the claimed drive, must exist) and `performedByUserId` existence, then inserts and returns the refreshed timeline.
- Endpoints: header CRUD `GET/POST /warranty-claims`, `GET/PUT/DELETE /warranty-claims/:id` (all `@Public()`, as before; `create`/`update` no longer accept status/timestamps). Read-only ledger `GET /warranty-claim-events` (paginated; dedicated filters `warrantyClaimId`/`eventType`/`performedByUserId`/`replacementPhysicalDriveId` + `eventTimestampFrom`/`To`) and `GET /warranty-claim-events/:id`, both `@Public()`. Nested `WarrantyClaimTrackingController` (`@Controller('warranty-claims')`): `GET /warranty-claims/:id/tracking` (`@Public()`, `WarrantyClaimTimelineResponseDto`) and `POST /warranty-claims/:id/tracking` (`CreateWarrantyClaimEventDto`, **authenticated**, `@CheckPolicy('create','warranty-claim-events')`) which returns the refreshed timeline. The actor comes from the token (`user.dbUser.id ?? user.id`).
- Reads expose derived **`currentStatus`**, **`openedAt`** (= `createdAt`) and **`resolvedAt`** (= the terminal event timestamp when `CLOSED`, else null), plus a shallow **`currentEvent`**, on every `WarrantyClaimResponseDto`: `WarrantyClaimService` injects `WarrantyClaimEventService.getStatusMap(claimIds)` and stamps them. `findAll` also includes `PhysicalDrive` + `Vendor` so the list has shallow drive/vendor labels, and supports a derived **`currentStatus`** filter (`eq`/`in`): `getClaimIdsByStatus` loads the claim ids + status map and the service rewrites the condition into `id IN (...)`. The tracking timeline responses also expose **`allowedEvents`** (legal state-changing events for the current status + `NOTE`). Policy `drives-policy/policies/warranty-claim-events.yaml` (admin `create`/`show`/`list`, owner/viewer read-only). Test fixtures `20261017041000-seed-test-warranty-claims.js` (6 headers) + `20261017042640-seed-test-warranty-claim-events.js` (13 events spanning `SUBMITTED`/`SHIPPED_TO_VENDOR`/`APPROVED`/`REJECTED`/`CLOSED` incl. an RMA replacement) — they resolve vendors by name, drives by id order, and upsert the mock user.
- **Create Warranty Claim workflow endpoint**: `POST /warranty-claims/initiate` (`CreateWarrantyClaimWorkflowDto` = `CreateWarrantyClaimDto` + required `datacenterId`; authenticated, `@CheckPolicy('create','warranty-claims')`, policy `drives-policy/policies/warranty-claims.yaml`). `WarrantyClaimService.openClaim` runs one transaction: verifies the drive is unseated (`ServerSlotAllocationService.getCurrentAssignmentsForDrives`) and its latest location is the selected datacenter, appends `DEPROVISION` when the drive is `IN_SERVICE` then `RMA_INITIATE` (the latter becomes the claim's `triggeringEventId`), creates the claim header, and appends an initial `NOTE` (`Warranty claim opened`) to the tracking log. ### Exchange rates

- `ExchangeRate` (`src/modules/exchange-rate`, table `exchange_rates`, migration `20260710065640-create-exchange-rates.js`) stores historical FX observations: `rateToUsd` DECIMAL(18,10) (USD per one unit), `effectiveAt` DATE, optional `source`, FK `currencyId` (→ `Currency`, CASCADE). Unique/index `exchange_rates_currency_effective_unique_idx` on `(currency_id, effective_at)`.
- `ExchangeRateService.getLatestRates(currencyIds?)` reads the newest `effective_at` row per currency (tie-broken by `displayKey DESC`). Currencies stay static reference data; rates are separate and append-only in practice.
- `ExchangeRateSyncService` pulls **Frankfurter v2** (`GET /v2/rates?base=USD&quotes=...`) once per hour at minute 0 UTC via `@nestjs/schedule` (`ScheduleModule.forRoot()` lives in `ExchangeRateModule`). It filters DB currency codes against `/v2/currencies` (cached 24h), stores `1 / rate` (USD per unit; `USD` is always `1`), uses the provider `date` as `effectiveAt`, sets `source = 'frankfurter'`, and upserts on `(currency_id, effective_at)` so hourly runs are idempotent and same-day provider corrections are applied. Requests use a 10s timeout and 3 attempts with backoff; errors are logged and swallowed so the scheduler can never crash the API.
- `ExchangeRateHousekeepingService` runs daily at 03:15 UTC and deletes rows older than `retentionDays` (default 730) while always retaining the latest row per currency (window-function delete). Both jobs use a process-local running guard plus a Postgres transaction-scoped advisory lock (`ExchangeRateLockService`) so multiple API replicas cannot run the same job concurrently; non-Postgres dialects skip the lock.
- Config (`src/config/exchange-rate.config.ts`): `DRIVES_BACKEND_EXCHANGE_RATE_SYNC_ENABLED` (defaults true except `NODE_ENV=test`), `DRIVES_BACKEND_EXCHANGE_RATE_API_URL` (default `https://api.frankfurter.dev`), `DRIVES_BACKEND_EXCHANGE_RATE_TIMEOUT_MS`, `DRIVES_BACKEND_EXCHANGE_RATE_RETENTION_DAYS`.
- Manual trigger: `pnpm --filter @drives/drives-server exchange-rate:sync` (`scripts/sync-exchange-rates.ts`).
- Baseline seed observations live in `20260710030320-seed-exchange-rates.js` (USD/EUR/GBP, including older rows so the latest-selection logic is exercised). The seeder resolves **managed** currencies by `code` (so it survives UUID changes and skips missing/unsupported ones) and inserts idempotently. A currency with no rate is treated as unconvertible, never as USD parity.

### Caching

- `CacheModule` (`src/modules/cache`, `@Global`) provides a fail-open **Valkey** (Redis-protocol) cache via `ioredis`. It is enabled outside `NODE_ENV=test` and can be disabled with `DRIVES_BACKEND_CACHE_ENABLED=false`; cache failures are logged and treated as misses so the API keeps serving from Postgres.
- `HttpCacheInterceptor` is a global interceptor. Opt a GET endpoint in with `@Cacheable({ tags: [...] })`; it caches the **already-serialized** 2xx response (the route-level `@Serialize` interceptor maps first on the response path) keyed by route + canonicalized query + tag versions. Cached hits return immediately and set `X-Cache: HIT` (misses set `MISS`).
- `CacheInvalidationInterceptor` reads `@InvalidateCache('tag', ...)` on mutations and increments the tag-version counter after a successful response, then returns. Tag versions (`tag:<tag>:version`) are part of every cache key, so invalidation is O(1) and works across API replicas without `KEYS`/`SCAN`; old entries expire by TTL. Invalidate after the write and await it so read-after-write cannot see stale data.
- `CacheService` owns TTL jitter (default 15 minutes), max response size (default 256 KB, oversized responses are skipped), tag reads/increments and fail-open behavior. `CacheKeyBuilder` canonicalizes/sorts query params and hashes the key.
- Currency and the reference-data modules (countries, vendors, capacities, interfaces, bus-protocols, storage-types, form-factors, pool-types, operating-systems, cpu-models, drive-models) are cached with per-resource tags; mutations invalidate their own tag. TTLs are intentionally short enough that direct DB/seed changes are picked up without manual invalidation.
- `GET /dashboard/summary` is cached for 30s under the `dashboard` tag. Drive CRUD/acquisition/relocation/location/lifecycle events, mount/unmount/slot saves/allocation workflows, physical-server/rack/datacenter mutations, warranty claim/tracking mutations, currency mutations, and exchange-rate syncs invalidate `dashboard`.
- `GET /physical-drives` (list/show) and `GET /physical-drives/:id/lifecycle` are cached for 30s under `physical-drives`. Drive CRUD/acquisition/relocation/location/lifecycle events, mount/unmount/slot saves/allocation workflows, and physical-server/datacenter mutations invalidate it. Both tags use the same version-counter invalidation described above.
- Config (`src/config/cache.config.ts`): `DRIVES_BACKEND_CACHE_ENABLED`, `DRIVES_BACKEND_VALKEY_URL`, `DRIVES_BACKEND_CACHE_KEY_PREFIX`, `DRIVES_BACKEND_CACHE_DEFAULT_TTL_MS`, `DRIVES_BACKEND_CACHE_COMMAND_TIMEOUT_MS`, `DRIVES_BACKEND_CACHE_CONNECT_TIMEOUT_MS`, `DRIVES_BACKEND_CACHE_MAX_RESPONSE_BYTES`.
- Local Valkey runs via `docker compose up -d valkey` (`valkey/valkey:8.0-alpine`, port 6379, `allkeys-lru`). Production should use a managed/persistent Valkey with auth/TLS and set the URL accordingly. Future waves can cache slot-assignment boards and other read-heavy resources with multi-tag invalidation.

Unique `(physical_drive_id, media_id)` plus a `(physical_drive_id, attachment_type)` index. `PhysicalDrive` has `media`, `Media` has `physicalDriveAttachments`.

### Content store

- `ContentStoreModule` (`src/modules/content-store`, `@Global`) is the storage abstraction behind `ContentStoreService` (SHA-256 content-addressed objects + JSON sidecar metadata). The public file endpoint remains `GET /files/:fileId` (immutable cache headers), used by generated assets and file previews.
- `ContentStoreProvider` (`interfaces/content-store-provider.interface.ts`) defines `put/get/exists/delete/list`. Two implementations:
  - `S3ContentStoreProvider` — existing S3-compatible object storage (`AWS_*` env vars; `forcePathStyle` defaults true).
  - `LocalContentStoreProvider` — filesystem/mounted-directory storage for single-node/small deployments. Writes are staged in `<root>/.tmp` and atomically renamed into place, keys are guarded against absolute paths/traversal, and `list` walks the requested prefix while ignoring staging files. The root defaults to `data/content-store` and is gitignored. `ContentStoreMaintenanceService` sweeps stale `.tmp` files at startup and every 6h (`DRIVES_BACKEND_CONTENT_STORE_TMP_MAX_AGE_MS`, default 1h, and `DRIVES_BACKEND_CONTENT_STORE_CLEANUP_INTERVAL_MS`, default 6h); active staging files younger than the max age are never touched.
- Driver selection (`src/config/content-store.config.ts`): `DRIVES_BACKEND_CONTENT_STORE_DRIVER=s3|local` (default `s3`), `DRIVES_BACKEND_CONTENT_STORE_LOCAL_PATH` for the local root, and optional `DRIVES_BACKEND_CONTENT_STORE_S3_*` overrides (falls back to `AWS_*`). The provider factory validates incomplete configuration at startup. For multiple API replicas, use S3 or a shared mounted filesystem; a node-local directory is not shared across replicas.
- `ContentStoreService` deduplicates by hash (`isNew: false` when the object already exists), stores `objects/<sha256>` + `objects/<sha256>.json`, and deletes both. `QRCodeStorageService` now injects `ContentStoreService` directly.
- `ContentStoreGcService` runs daily at 04:00 UTC (and uses a process guard plus a Postgres transaction-scoped advisory lock): it compares `objects/<sha256>` entries with `media.file_id` (including soft-deleted media), and deletes unreferenced objects older than `DRIVES_BACKEND_CONTENT_STORE_GC_GRACE_MS` (default 24h), capped by `DRIVES_BACKEND_CONTENT_STORE_GC_BATCH_SIZE` (default 500). Disable with `DRIVES_BACKEND_CONTENT_STORE_GC_ENABLED=false`. This is the reconciliation half of the content pipeline: content is written before the DB transaction, so a failed transaction can only leave reusable content objects, which GC reclaims.

Indexes `audit_logs_resource_target_idx` (`resource, resource_id, timestamp`), `audit_logs_chronological_idx`, `audit_logs_user_idx`.
- `userId` is the Keycloak subject (`sub`) and is **deliberately not** a FK to `users` (the `20260710055000-create-audit-logs.js` migration defines `user_id` without `references`): audit entries are append-only and must not fail when the actor is unprovisioned or their user row is later removed.
- Endpoints (authenticated — **not** `@Public()`; guarded by `KeycloakAuthGuard`/`CerbosGuard` and gated by `@CheckPolicy('create'|'list', 'audit-logs')`; policy `drives-policy/policies/audit-logs.yaml`): `POST /audit-logs` (`CreateAuditLogDto`) and `GET /audit-logs?resource=&resourceId=&action=&userId=` returning `{ data, total }` (whitelisted sort/filter via `QueryAuditLogDto`). The acting operator is taken from the validated token (`@RequestUser()`), **not** the body — `CreateAuditLogDto.userId` is only an anonymous/system fallback and is stored solely when it is a well-formed UUID. Serialized with `@Serialize(AuditLogResponseDto)` — the nested `payload` needs its own `@Expose()` on `previous`/`current`, **plus** a `@Transform(({ obj, key }) => obj[key])` passthrough: `excludeExtraneousValues` otherwise collapses the arbitrary `Object`-typed delta maps into `{}` (the same quirk affects `drive-lifecycle-event.contextMetadata`). `findAll` batches a `User` lookup (the module registers `User` alongside `AuditLog`) to decorate each row with a resolved `userName`, since the `/users` resource is admin-only and not exposed to the UI.
- UI integration: `drives-ui/src/providers/audit-log-provider` implements `AuditLogProvider`, adapting Refine's `{ data, previousData, meta.id, author }` ⇄ the server's `{ payload: { previous, current }, resourceId, userId, userName }` (and collapsing `*Many` actions to the singular verbs). It does **not** send `userId` — the server derives the author from the access token. It is passed to `<Refine auditLogProvider=…>` in `_refine_context.tsx`, so every `useCreate`/`useUpdate`/`useDelete` logs automatically; the System-menu page `/audit-logs` (`src/app/audit-logs/page.tsx`) reads via `useLogList` and renders `author.name` (falling back to the `userId` sub).

### Authorization & roles (RBAC)

- Roles are **`admin`**, **`user`**, **`viewer`** (Keycloak realm or client roles; `owner` is retired, migrated to `user`).
- `admin` manages all resources, reference data and admin tools (tasks, audit logs, users); managed reference rows stay immutable.
- `user` has read access to inventory plus the guided workflows, but **no direct create/edit/delete** and no direct custom actions. Workflow-only actions: `physical-drives:acquire|relocate|manage-media`, `drive-models:create-workflow`, `physical-cpus:acquire`, `cpu-models:create-workflow`, `warranty-claims:initiate`, `warranty-claim-events:track`, `server-slot-allocations:allocate`, and UI `workflows:run`.
- Admin-only direct custom actions: `physical-drives:locate`, `drive-lifecycle-events:create`, `server-slot-allocations:mount|unmount|save`, `storage-pools:import|export`, `tasks:*`, `audit-logs:*`.
- `viewer` is read-only (`list`/`show`) and cannot run workflows. Reference-data lists/shows remain readable.
- Public allowlist: all `/health*`, `/system/status`, `/system/version`, `/files/:fileId`, `/metadata/managed-resources`. The UI `/system/status` page is also public (no session redirect); `/system/tasks` remains admin-only.
- Never combine `@Public()` with `@CheckPolicy()`: a public route skips user attachment, so Cerbos cannot evaluate it. Protected controllers use `@CheckPolicy(action, resource)`; policies live in `drives-policy/policies/` (notably `workflows.yaml`, `warranty-claim-events.yaml`, `users.yaml`).
- UI enforcement mirrors the backend: Refine's `accessControlProvider` calls `/api/permissions`, `ThemedSider` hides resources without `list`, `CreateButton`/`EditButton` hide without `create`/`edit`, `ResourceRouteGuard` blocks direct create/edit URLs and admin-only pages, `WorkflowAccessGuard` + `WorkflowLauncher` hide workflows without `workflows:run`, and custom actions (locate, attach drives, import/export, warranty tracking) render only when `useCan` allows them. The backend remains the authority.

### Database

- Dev config has `synchronize: true` (auto-syncs schema); prod is `synchronize: false` and relies on migrations.
- Migrations/seeders: `src/database/migrations|seeders`, run via sequelize-cli with `node --env-file=.env`:
  `pnpm --filter @drives/drives-server migration:run`, `migration:generate --name <name>`, `seed:run`. Also `db:sync` (`scripts/sync-database.ts`, dev-only schema sync). Filenames use the `YYYYMMDDHHMMSS-…` format, spaced 1000 seconds apart, in three independent sequences: migrations, production seeders and test seeders. Migrations are pure `createTable` steps ordered so every FK target exists first; keep new migrations at the end of the sequence.
- **Test fixtures** live in `src/database/test-seeders/` (separate from production `seeders/`): `pnpm --filter @drives/drives-server seed:test` (`db:seed:all --seeders-path src/database/test-seeders`) and `seed:test:undo` (undoes by basename of every file in that dir; it only removes rows owned by the fixture and can fail when app-created rows still reference them). For a clean test dataset use **`seed:test:reset`** (`seed:test:teardown` then `seed:test`): `scripts/teardown-test-data.js` truncates every test/app data table (logs first, `CASCADE`, `RESTART IDENTITY`), preserves production reference data and `users`, and clears the test-seeder rows from `sequelize_data` so the fixtures run again. Files run in timestamp order: datacenters → cpu-models → drive-models → racks → physical-servers → physical-cpus → physical-drives → server-slots → virtual-servers → passthrough-slots → storage-pools → storage-pool-hosts → physical-drive-locations → server-slot-allocations → drive-lifecycle-events → warranty-claims → warranty-claim-events. The fixture provides **3 datacenters**, 4 racks, 7 physical servers, 66 slots, 50 drives, 10 guests and 8 storage pools, with 6 live mounts (two per datacenter), 8 allocation events and 136 lifecycle events. The `physical-cpus` seeder runs after `physical-servers` and resolves the owning server by hostname, so it sets `physical_cpus.physical_server_id` at insert (the server rows already exist). The `physical-drives` fixture seeds **50 drives**: 6 curated rows (serial numbers like `S6BZNA0T512345`, referenced by the downstream location/allocation fixtures) plus 44 deterministically generated rows for paging/list/board testing. `lib/lookups.js` exposes `idMap(queryInterface, table, keyColumn='name')` / `required(map, key, table)` to resolve FKs by business key; ids are deterministic UUIDv7-shaped values; `bulkInsert` bypasses model hooks so denormalised `absolute_*memory` columns must be set explicitly. sequelize-cli's loader is **non-recursive** (so `lib/` is safe) and `db:seed:undo --seed` matches by **basename**; `executed()` lists ALL executed seeders.
- Local infra via `docker compose up` (`compose.yaml`): Postgres 18 on 5432, Valkey on 6379, Adminer on 8080, Cerbos on 3592 (HTTP) / 3593 (gRPC).
- Cerbos reads policies from `drives-policy/policies/` (`cerbos.yaml`, mounted in compose). Add a `.yaml` policy there for a new protected resource. Policies that gate `edit`/`delete` on `request.resource.attr.managed` rely on a **derived** list, not a hardcoded one: `ManagedResourcesService` (`src/modules/metadata`, `@Global`) introspects the Sequelize models at bootstrap and collects every model with a `managed` attribute (table name kebab-cased → resource slug, e.g. `pool_types` → `pool-types`). The server's `CerbosGuard` uses it to decide whether to send the `managed` attribute, and it is exposed at `GET /api/v1/metadata/managed-resources` (public, versioned) for the UI's `access-control-provider`, which fetches it once instead of hardcoding `MANAGED_RESOURCES`. So a new managed lookup is picked up automatically as soon as its entity declares a `managed` column (the actual protection of managed rows is still enforced in the services with a 409).

## Frontend (`drives-ui`)

- `src/proxy.ts` is Next 16's renamed middleware: rewrites `/api/proxy/*` to `DRIVES_FRONTEND_API_URL` and serves `/api/health`.
- Data access goes through `src/providers/data-provider` → `/api/proxy` (auth via NextAuth session token; auto-retries on 401/403). REST resources map 1:1 to backend routes.
- Every resource layout passes `Sider={AppSider}` (`src/components/app-sider.tsx`). It replaces Refine’s `ThemedSider` with an antd `Menu items`-based sider (the default still uses deprecated `Menu.Item`/`Menu.SubMenu` children) while keeping permission-filtered menu entries, collapse state and the mobile drawer. Logout lives in the header user menu.
- Dashboard charts use **Recharts** (`recharts`) in `src/app/dashboard/_components/`, rendered inside antd `Card`s and colored from `theme.useToken()` + the AntV categorical palette so both light/dark modes stay legible. The lower half of `/dashboard` starts with the presentational "Physical Drive Distribution" donut, followed by the **Warranty Watchlist**, **Fleet Lifecycle Health**, **Slot Utilization**, **RMA Pipeline**, **Capital & Age**, **Datacenter Health Matrix**, **Oldest In-Use Drives** and **Recent Activity** cards fed by `GET /dashboard/summary` (all in the same directory; the old placeholder sales/stock widgets were removed).
- Reference-data dropdowns (countries, vendors, bus-protocols, currencies, …): use `@components/lookup-select` (`LookupSelect`) in forms and `@hooks/use-lookup-options` (`useLookupOptions`) in list-page filters/renders. Both fetch the resource's rows up front (one server page, default 100) and let Ant Design filter client-side. Avoid Refine's `useSelect` — its `pagination.mode` defaults to `"off"`, so the API falls back to `pageSize: 10` and typing never filters.
- Foreign-key columns/fields that have their own show page use `@components/linked-label` (`LinkedLabel`): pass `resource` + `value` (plus `options` to resolve the label, or an explicit `label`). It renders a `Typography.Link` opening `/{resource}/show/{value}` in a new tab with an `ExportOutlined` cue, falling back to `Loading...`/`-` when the value or label is unresolved. Used by the CPU-models, datacenters, interfaces, physical-drives, physical-servers, racks, drive-models, storage-pools, vendors, and virtual-servers list/show pages.
- Theme: `src/contexts/color-mode` holds both the light/dark `mode` and a user-selectable `colorPrimary` (`PRIMARY_COLOR_PRESETS`); both persist in `theme`/`primaryColor` cookies, are seeded on the server in `src/app/layout.tsx`, and are toggled from `src/components/header` (dark-mode `Switch` + color `Dropdown`), and logout is under the top-right user dropdown (`src/components/user-profile-display`). The favicon is updated client-side by `src/components/dynamic-favicon` to use the active `colorPrimary`. The sidebar/login title icon (`AppLogo` in `src/app/_refine_context.tsx`) is a `lucide-react` `HardDrive` tinted with the active `colorPrimary` via `theme.useToken()`, matching the `favicon.svg` drive glyph.
- **Workflows**: reusable guided-wizard system in `src/components/workflow` (`WorkflowWizard` = theme-aware antd `Steps` + `Form` shell with per-step validation; `WorkflowLauncher` = data-driven dashboard cards). The dashboard renders `WORKFLOWS` from `src/workflows/registry.tsx` in a **Workflows** section at the top; add a registry entry + a page under `src/app/workflows/<key>` (with its own `layout.tsx`) to add a workflow. First workflow: **New Drive Acquisition** (`/workflows/drive-acquisition`) — 5 steps (Hardware → Purchase → Receiving → **Media (optional)** → Review) that prefetch vendors/drive-models/currencies/datacenters, filter models by the selected manufacturer, and derive a preview. After selecting a manufacturer the user can either pick an existing model or open the nested **Create a new drive model** modal (model details → review). It collects the full drive-model payload (manufacturer is fixed from the parent step), posts to `POST /api/proxy/drive-models/workflows` (Cerbos action `create-workflow`; `user` and `admin` allowed), adds the created model to the current options, selects it in the parent form, and refetches the drive-models list. The optional media step accepts drag/drop or browse (up to 20 files, 25 MB each), per-file notes, attachment type and one primary flag. It then `POST /api/proxy/physical-drives/acquisitions` via `useCustomMutation`; after the drive is created it uploads the staged files to `POST /api/proxy/physical-drives/:id/media` (best-effort, with a warning notification if attachment upload fails) and redirects to the drive show page. The acquisition endpoint itself remains atomic (drive + location + ACQUIRE event). Second workflow: **Relocate Drive** (`/workflows/drive-relocation`) — source datacenter (or **Unassigned**) → drive → target datacenter → review; it lists drives via the `currentLocation`/`unassigned` filters, hides drives with a `currentAssignment` (mounted drives must be unmounted on the server's Assign Drives page first), then `POST /api/proxy/physical-drives/:id/relocations` and redirects to the drive show page. Third workflow: **Drive Allocation** (`/workflows/drive-allocation`) — datacenter → optional source server (check drives to detach) → optional target server (drag detached/unseated drives onto its slots via `@dnd-kit`) → **Detached states** (for each detached drive left unseated, pick a legal reason from `currentLifecycle.allowedEvents` ∩ the curated set and an optional explanation) → review; it reads both boards through `useCustom`, then `POST /api/proxy/physical-servers/allocations` and redirects to the target (or source) server show page. The endpoint applies all unmounts/mounts/lifecycle events atomically. Fourth workflow: **Create Warranty Claim** (`/workflows/create-warranty-claim`) — datacenter → unseated/RMA-eligible drive → vendor/RMA #/notes → review; it reads the drive list via the `currentLocation` filter and filters to unseated drives whose `warrantyExpiryDate` is today or later and whose `currentLifecycle.allowedEvents` permit `RMA_INITIATE` (or `DEPROVISION` when `IN_SERVICE`), excluding drives with a non-`CLOSED` claim from the claim list, then `POST /api/proxy/warranty-claims/initiate` and redirects to the claim show page (expired warranties and existing open claims are hidden in the picker and rejected by the endpoint with 409). Fifth workflow: **Progress Warranty Claim** (`/workflows/progress-warranty-claim`) — datacenter → in-progress claim (not `CLOSED`, drive currently located in that datacenter) → next tracking event (only the timeline's `allowedEvents`, optional timestamp/notes, replacement-drive picker for `REPLACEMENT_RECEIVED`) → review; it fetches the claim's tracking timeline via `useCustom` to show the current status/latest event, then `POST /api/proxy/warranty-claims/:id/tracking` and redirects to the claim show page. Sixth workflow: **Drive Media Management** (`/workflows/drive-media-management`) — datacenter → searchable drive in that datacenter → staged media step (current attachments with previews, notes/type/primary editing, remove/restore, plus new drag/drop files with per-file notes/type/primary) → review; nothing is applied until submit, then applies everything through the unified `PUT /physical-drives/:id/media` call (add/update/remove sections) before redirecting to the drive show page. Seventh workflow: **New CPU Acquisition** (`/workflows/cpu-acquisition`) — manufacturer → CPU model (choose existing or open the nested create-model modal) → serial number → purchase details → review; it posts to `POST /api/proxy/physical-cpus/acquisitions` (Cerbos action `acquire`) and redirects to the CPU show page. New CPU models are created through `POST /api/proxy/cpu-models/workflows` (Cerbos action `create-workflow`); both actions are available to `user` and `admin`.
- Path alias `@*` → `src/*` (plus `@allocations/*`, `@products/*`, `@purchase-orders/*`).
- Formatting: UI uses default Prettier (double quotes); server has `.prettierrc` with `singleQuote`/`trailingComma: all`. Run `turbo run format` or per-package `format`.
- Virtual-servers form (`src/app/virtual-servers/_components/virtual-server-form.tsx`) demonstrates the guest conventions: it fetches `physical-servers` whole (with `slots` and `cpus`) to scope the passthrough editor, and `cpu-models` to derive the host's total threads (sum of the host's installed `cpus`' `cpuModel.threads`) and cap the Allocated vCPUs field; it clears passthrough rows on host change and hides the editor (showing a notice) for `type: CONTAINER`. Passthrough rows use `EditableProTable` — add an explicit `valueType: "option"` column, since it does not auto-generate one (while editing it is replaced by the built-in Save/Delete/Cancel actions).
- Storage-pools form (`src/app/storage-pools/_components/storage-pool-form.tsx`) shows an optional "Initial Host" `Radio.Group` (component state, no form field) toggling a `serverId`/`virtualServerId` `LookupSelect` **on create only** (`mode: "create"`); edit hides it because host changes are recorded through the show page's Import/Export actions. Both `Form.Item`s stay mounted (only one visible via `hidden`) and the type switch sets the inactive field to `null`, so the payload never carries two hosts. Route pages pass Refine's `form` instance into the form (`const { formProps, form, saveButtonProps } = useForm({})`), matching `virtual-servers`. The show page (`_components/storage-pool-host-actions.tsx`) drives `POST /storage-pools/:id/import|export` via `useCustomMutation` and renders the `hosts` timeline (`_components/storage-pool-hosts-timeline.tsx`), refetching with `query.refetch()`. The list column shows the derived `currentHost` (`Detached` tag when null); `@components/attached-storage-pools` (used by the physical/virtual-server show pages) lists a host's currently attached pools via `GET /storage-pools/attached`.

## Env & deployment
